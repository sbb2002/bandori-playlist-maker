## 작업 순서

1. **아티팩트로 (energy, valence) 2D 세부설정 UI 프로토타입 제작**
   - report_final.md의 "arousal-valence 2D 맵(circumplex)" 제안을 아티팩트로 먼저
     시각화/프로토타이핑 — 실제 코드 반영 전에 UX를 검증.
2. **1)을 실제 앱에 적용 + 다른 파라미터 도입**
   - 2D 맵 UI를 `src/frontend`의 세부설정 화면에 실제로 반영.
   - 나머지 채택 파라미터(lufs_integrated, lra, danceability_norm, instr_stem_ratio,
     speech_median, acoustic_median 토글, mode 필터)도 순차 도입.
   - **정서 지도 배경 테마(2026-08-02 결정, 3안 모두 킵)**: 프로토타입에 배경 3안(1=현재
     accent 코너 라디얼, 2=사분면 4색, 3=EMOI-MAP풍 딥스페이스+별/성운)을 토글로 구현해
     비교함 — 3안 모두 유지하기로 함. 앱 반영 시 **기본값은 1안**, 추후 "설정"에서 사용자가
     2·3안 중 테마를 고를 수 있게 함(지금 단계에서 설정 UI까지 만들지는 않음). 3안(EMOI-MAP풍)은
     실제 앱에서 캔버스 BPM 펄스 애니메이션은 쓰지 않지만, 정적 데이터 포인트(별) 자체는
     구현할 예정 — 프로토타입의 CSS 정적 별은 최종본이 아니라 자리표시자.
   - **선곡 엔진 보간 로직(2026-08-02 설계 확정, 미구현)**: 구간(스테이지)의 값은 고정값이
     아니라 구간 경계점 사이를 점진적으로 보간(interpolate)한 궤적으로 다룬다. 예:
     1구간 포인트(energy=28, valence=32, loudness=30, lra=62, ...) → 2구간 포인트
     (energy=40, valence=55, loudness=48, lra=55, ...)로 급변하지 않고 점진적으로 변화.
     1구간에 곡이 3곡 배정됐다면 3곡 모두 "1구간의 고정값"으로 선곡하는 게 아니라, 1구간
     내에서 점진적으로 변화하는 세부 목표값에 따라 각 곡을 선곡한다.
     **주의**: 아직 효용성(실제 청취감 개선 여부) 검증 전이므로 이 보간 방식을 **메인
     옵션**으로, 기존 구간별 고정값 방식은 **보조 옵션**(A/B 비교·폴백용)으로 함께 구현할 것.
     선곡 엔진(도메인 순수 함수, PRD §8 하모닉 믹싱 규칙과 같은 위치)에 반영되는 로직이라
     2)의 앱 반영 범위에 포함되지만, 프론트 UI(1단계 프로토타입)와는 별개로 별도 구현 필요.
3. **외부 LLM 어댑터의 파라미터 제어 로직 수정**
   - 현재(`src/backend/app/adapters/groq_adapter.py` 등)는 단일 응답으로 파라미터를 한 번에
     채우는 방식까지만 구현됨.
   - 사용자 청취감과 괴리가 확인되면(추후 판단), 파라미터를 여러 단계로 나눠 제어하는 방식으로
     확장 — **multistage가 그 스켈레톤**(기존 에너지 단계 로직 재사용 가능한 뼈대로 참고).
   - 지금 단계에서 바로 분할 제어를 구현하지는 않음 — 필요성이 확인된 이후 착수.
3.5. **[결정, 2026-08-03] 단일응답 어댑터 우선 — 청취 전 "버려지는 파라미터" 먼저 해소**
   - 오너 결정: multistage로 바로 넘어가지 않는다. **먼저 단일응답 어댑터
     (`groq_adapter.py`+`prompt.py`)에서 AI 모드가 버리는 파라미터가 없도록 수정**한 뒤
     4) 청취 테스트를 진행한다.
   - "버려지는 파라미터"란 구체적으로: 요청 스키마(`MoodParameters`)에 구간별 길이(분)
     필드가 없어서, 사용자가 프롬프트로 표현한 구간 길이 의도(예: "마지막 5분은
     릴랙스")가 애초에 LLM에게 물어지지도 않고 사라지는 문제. 상세 원인은 아래 "알려진
     제약" 및 `docs/WIP_multistage-stage-params-plan.md`의 "도메인 변경" 절 참고.
   - **순서**: 3.5) 단일응답 스키마/도메인 갭 해소 → 4) 청취 테스트(단일응답 방식의
     성능을 먼저 검증) → 그래도 청취감이 별로면 그때 3)의 multistage로 어댑터를 교체.
     multistage는 단일응답을 **대체**하는 별개 구현이지 병행 폴백이 아님 — 검증 없이
     먼저 넘어가지 않는다.
4. **main vs epic 청취감 비교 → epic 우수 판정 시 머지**
   - `epic/improved-playlist-maker`(epic versioning)에서 완성된 버전과 현재 `main`을
     실제 청취 비교.
   - epic 쪽이 우수하다고 판단되면 그때 `main`으로 머지 시도(리뷰·PR 절차는 CLAUDE.md
     working agreement 따름 — owner 머지, 임의 머지 금지).

### 다음 작업 순서 (오너 결정, 2026-08-03) — 메인 로컬/새 세션 인수인계

1. **먼저 단일응답 어댑터의 "버려지는 파라미터" 문제부터 고친다.** multistage로 바로
   전환하지 않는다.
   - 구체적으로: `MoodParameters`에 구간별 길이(분) 필드(가칭 `stage_minutes`)를 신설하고,
     `prompt.py`의 시스템 프롬프트에 이를 요청하는 지시를 추가하고, `domain/selection.py`의
     `_stage_targets_and_counts()`(L223)에 `stage_minutes`가 있으면 곡 개수를 분(길이)
     비율로 배분하는 분기를 추가한다(현재는 `stage_energies`만 있어도 곡 개수를
     `distribute_counts()`로 거의 균등 배분 — 이게 "마지막 5분 릴랙스" 같은 요청이
     반영 안 되는 근본 원인, 아래 "원인" 절 참고).
   - 서버 측 구간 최소 길이 하한도 함께 고려(현재 프론트 `app.js`의
     `MIN_WIDTH_MIN = 3`과 동일 기준 — 커스텀 모드는 프론트에서만 강제하고 서버는
     무방비 상태, AI 모드 신규 필드에도 같은 하한이 필요할지 검토).
   - 상세 설계 초안(도메인 변경 지점, 신규 필드 이름 후보 등)은
     `docs/WIP_multistage-stage-params-plan.md`의 "도메인 변경" 절 참고 — 원래 그
     문서는 multistage 차용 전제로 쓰였지만, 도메인 변경 부분(`stage_minutes` 신설 +
     `_stage_targets_and_counts()` 분기)은 단일응답 경로에도 그대로 필요한 공통 작업.
2. **그 다음 4) 청취 테스트를 진행한다.**
3. **청취 후에도 여전히 의도 반영이 부족하다고 판단되면, 그때 3) multistage 분할 제어로
   전환한다.** multistage는 단일응답 방식을 **대체(교체)**하는 별개 구현이다(폴백/보조 옵션이
   아니라 어댑터 자체를 갈아타는 것). 지금은 먼저 단일응답 방식의 성능(청취감)을
   검증하는 단계 — 검증도 안 해보고 multistage로 먼저 가지 않는다(오너 명시적 결정).

### 원인 (참고 — 위 3.5)가 왜 필요한지)

실측 재현 프롬프트("60분동안 점점 숨차는 운동에 어울리는 노래로 해줘. 마지막 5분은
릴랙스하게.")에서 4구간 모두 균등 15분 배정 + stage_params 소극적 안주 관찰됨.

- **구간별 길이(분)는 프롬프트 문제가 아니라 스키마/도메인 갭.** 단일응답 어댑터
  (`groq_adapter.py`+`prompt.py`)의 요청 스키마엔 애초에 "구간별 길이(분)" 필드가
  없어서 LLM에게 묻지도 않는다. `groq_multistage_adapter.py`(실험용)는 2차에서 구간별
  길이를 받아오긴 하지만 최종 조립에서 버린다 — `domain/selection.py`의
  `_stage_targets_and_counts()`가 곡 **개수**만 거의 균등 배분(`distribute_counts()`)
  하고, `MoodParameters`에 구간별 길이를 받을 필드 자체가 없기 때문. **프롬프트를 아무리
  잘 써도 못 고치는 아키텍처 갭이며, multistage로 전환해도 이 필드가 없으면 똑같이
  버려진다** — 그래서 오너가 "먼저 단일응답에서 이 갭부터 메운다"고 결정함(위 순서 참고).

  조치로 `[지표 분포 통계]`(전체/밴드별 min/max/mean/median/std)를 시스템 프롬프트에
  주입(커밋 `4eb143f`)해 "조용한 발라드" vs "Roselia 격렬" 같은 뚜렷한 대조에서는 효과
  확인됨. 다만 한 번의 거대 JSON 응답에 필드가 너무 많으면(십수 개) 다시 평이해지는
  경향 남아있음 — 3.5) 작업으로 필드가 하나 더 늘면(구간별 길이) 이 경향이 더 심해질
  수 있다는 점도 3.5) 구현 시 함께 확인할 것(프롬프트 지시 배치·예시 조정으로 완화
  시도, 그래도 안 되면 이것이 multistage 전환을 판단하는 근거 중 하나가 됨).
