# archive/version/ — 배포판 로직 스냅샷의 버전 관리 규칙

`archive/last-papers/reports/`가 "특정 시점 기록·다음 패치 아이디어" 티어라면, 이
`version/` 아래는 **"현재 배포판이 실제로 서비스하는 로직을 한 곳에 모은 스냅샷"** 티어다.
`version` 브랜치(`README.md` 버전 이력)와는 별개— 그쪽은 "언제 어떤 버전이 나갔는가"의
연대기이고, 여기는 "그 버전이 지금 뭘 하고 있는가"의 최신 상태 문서다.

폴더는 `main`의 Major 버전 하나당 하나(`v2/`, 다음 Epic이면 `v3/` ...). 폴더 안 `.md`
파일 하나가 로직 하나(프롬프트→플리 생성, 오마카세 버튼 등)에 대응한다.

## 갱신 규칙 — main에 반영된 패치 등급에 맞춰

| main 쪽 변경 등급 | 이 폴더에서 할 일 |
|---|---|
| **Epic**(`epic/*`, Major 버전 올림 — 구조 개편·전면 개편) | 새 `version/v<N>/` 폴더를 **처음부터 다시 작성**한다. 옛 `v<N-1>/`은 손대지 않고 그대로 히스토리로 남긴다. |
| **Minor**(`feature/*`, Minor 버전 올림 — 새 기능 추가) | 현재 `v<N>/` 폴더에 **그 기능만 다루는 새 파일**을 추가한다(예: `05-새기능.md`). 기존 파일은 안 건드린다. 인덱스(`v<N>/README.md`)에 링크 추가. |
| **Minor — 기능 제거**(기존 기능이 통째로 빠짐) | 파일을 지우지 않고 `~~~(deprecated).md`로 이름을 바꾼다(예: `02-omakase-button-logic(deprecated).md`). 내용은 그대로 두거나 맨 위에 제거 사유·시점만 한 줄 추가. 인덱스에서 "폐기됨"으로 표시. |
| **Patch**(`hotfix/*`/`patch/*`, Patch 버전 올림 — 기존 로직 수정) | 해당 로직을 다루는 **기존 파일을 직접 수정**한다(새 파일 안 만듦). 다이어그램·표가 실제와 달라졌으면 그 자리에서 고친다. |

새 로직 문서를 쓸지 말지는 기존 기준을 유지한다: 짧지 않고 외부 API 호출 한 줄로 안
끝나는 로직만 문서화한다(각 `v<N>/README.md` 하단에 "생략한 이유" 명시).

## 왜 last-papers와 분리하나

`last-papers/reports`는 코드 리딩 세션에서 파생된 시점 기록이라, 이후 코드가 바뀌면 그
문서는 "그때는 맞았다"는 상태로 자연스럽게 낡아간다(실제로 여러 문서가 그런 갱신 코멘트를
달고 있음). `version/`은 반대로 **항상 현재 배포판과 일치해야 하는** 문서라서, 코드가
바뀌면 last-papers처럼 새 문서를 쌓는 대신 이 폴더의 해당 파일을 그 자리에서 고친다(Patch
행) — "지금 배포판이 뭘 하는지 알고 싶으면 last-papers 전체를 훑지 말고 이 폴더 하나만
보면 된다"는 게 존재 이유다.
