TPM Queue Monitor

Groq는 openai/gpt-oss-20b에 분당 8,000토큰(TPM) 한도를 건다. 요청 1건의 고정 비용만 ~5,600토큰이라, 두 번째 요청부터는 그냥 기다려야 한다. 예전엔 이 대기를 HTTP 요청 안에서 블로킹하다 20초 만에 429로 끊었는데, 이제 JobStore가 잡을 등록하고 즉시 202를 준 뒤 백그라운드에서 실제 예산이 찰 때까지 기다린다 — 아래는 그 실측 로그와, 같은 메커니즘을 재생해보는 시뮬레이션이다.

실측 — 2026-08-10 로컬 세션 curl, 동일 프롬프트 3건 연타
bash — POST /api/setlist × 3, 이어서 GET status 폴링 
$ curl -sX POST .../api/setlist  # req1
{"job_id":"a9eba17f…","estimated_wait_seconds":0.0,"queue_position":0}

$ curl -sX POST .../api/setlist  # req2, 0.1초 뒤
{"job_id":"e52f1d1d…","estimated_wait_seconds":7.0,"queue_position":1}

$ curl -sX POST .../api/setlist  # req3, 또 0.1초 뒤
{"job_id":"4d540c5f…","estimated_wait_seconds":6.9,"queue_position":2}

$ watch curl .../api/setlist/status/4d540c5f…  # req3 폴링 (1초 간격)
running  wait=28.9s  ahead=2
running  wait=27.7s  ahead=2
running  wait=25.2s  ahead=2
running  wait=22.7s  ahead=2
running  wait=19.1s  ahead=2
running  wait=15.0s  ahead=2
running  wait=13.8s  ahead=2  ← req1이 아직 안 끝나 ahead=2 그대로
   ⋮
req1 → done
running  wait=33.2s  ahead=0  ← req1·req2 끝나 ahead=0인데, req2가 방금 예산을 더
running  wait=31.8s  ahead=0    가져가 wait는 오히려 늘어남(근사치라 이런 역전이 있음)
done     result: {"params": {...}, "picks": [...] }

req3의 대기시간이 13.8초→33.2초로 늘어난 구간이 핵심이다 — estimated_wait_seconds는 "지금 이 순간" 남은 예산 기준 근사치일 뿐, 순번을 예약해두지 않는다. req2가 먼저 깨어나 토큰을 가져가면 req3의 실제 대기는 늘어날 수 있다. 그래도 queue_position(몇 명 앞섰는지)은 끝난 잡만 정확히 빠지므로 신뢰할 수 있다.
