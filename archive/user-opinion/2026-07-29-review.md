# 문제점
1) 1번 항목
    * _build_interpreter()에서 router를 통과한 후 apikey 검증없이 기동하는데, 만약 invalid key인 경우 다른 라우터로 대체하거나 알람을 주는 fallback이 없음. 아래 중 하나로 권고.
        - 현재 라우터(groq)가 실패할 경우 대체 라우터(openrouter)로 대체
        - 현재 라우터(groq)가 실패할 경우 telegram으로 알람 보내기. 특히 응답상태코드와 현 위치에서의 에러는 apikey가 invalid해서 발생한 것임을 꼭 알려주기.
    * **[Claude 코멘트, 2026-07-29]** "알람이 없다"는 전제는 정확하지 않음 — invalid key(401)는
      `LLMUpstreamError`로 매핑돼 502 핸들러가 이미 `_alert()`를 호출함(`main.py:365-368`).
      실제로 빠진 건 "원인 특정"뿐 — 지금은 네트워크 오류든 invalid key든 전부 "LLM_UPSTREAM
      502"라는 같은 제목으로 뭉뚱그려짐. 조사 중 `src/backend/app/adapters/openrouter_adapter.py`가
      이미 존재하지만 `main.py`의 `_build_interpreter()` 어디에서도 import 안 되는 **죽은
      코드**임을 발견(`MOOD_INTERPRETER=openrouter`를 넣어도 실제로는 Groq 어댑터가 생성됨).
      `.env.example`도 여전히 `OPENROUTER_*` 변수를 예시로 남겨둔 낡은 상태 — 둘 다 Groq로
      벤더가 확정되기 전(CLAUDE.md "Resolved" 이전)의 흔적으로 보임. **자동 페일오버(대체
      라우터)는 추천하지 않음** — invalid key는 대부분 설정 실수지 일시적 장애가 아니라서,
      자동으로 다른 벤더로 넘어가면 오히려 설정 실수를 더 오래 못 알아챌 위험이 있고, 죽어있는
      어댑터를 되살리는 별도 작업이 필요함(리뷰 대상도 안 됐을 코드). 대신 **알람 제목/본문에
      상태코드(401)를 명시**하는 쪽을 추천 — 비용 대비 효과가 훨씬 큼. `openrouter_adapter.py`·
      `.env.example`의 낡은 항목 정리는 이 항목과 별개의 소규모 청소 작업으로 분리 추천.
    * **[저장소 소유자 코멘트, 2026-07-29]** option B가 내가 봐도 맞아. 알람을 구체화하는
      수준으로 하면 될거같아.

2) 4a 항목
    * Queue overload 시 새로운 사용자가 요청할 경우 대기처리하는 fallback없이 503처리.
        - 대기 큐 처리를 구현할 것. 단, 큐의 maxlen=100이며 이를 초과한 요청에 대해서는 현재처럼 나중에 다시 이용해달라고 안내 후 튕겨낼 것.
        - 저장된 큐 길이가 10 이상일 경우 5분마다(최초 포함) 알람을 보낼 것.
    * **[Claude 코멘트, 2026-07-29]** 방향(진짜 큐잉)엔 동의하지만 우선순위엔 의문. Inflight
      상한(200, 동시)과 Groq 페이싱 상한(`GROQ_RATE_PER_MIN`=25, 분당)의 스케일 차이가 커서,
      실제 트래픽 몰림은 200 동시접속까지 가기 훨씬 전에 25/분 페이싱(3b/4b의 429)에 먼저
      걸릴 가능성이 큼 — 즉 지금 상태로는 4a(503)가 실제로 발동할 일 자체가 드물 수 있음.
      또한 여기 적힌 `maxlen=100`이 이미 존재하는 `TokenBucketLimiter`의
      `rate_max_waiters=100`(Groq 페이싱 레이어의 대기열 상한)과 정확히 같은 숫자라, 혹시
      이 제안이 Inflight(동시처리) 레이어가 아니라 이미 있는 Groq 페이싱 레이어를 염두에 둔
      것인지 확인이 필요함 — 그렇다면 "새 큐를 만드는" 게 아니라 "이미 있는 큐에 관측성(길이
      추적·알람)만 붙이는" 훨씬 작은 작업이 됨. 실제로 503이 프로덕션에서 한 번이라도
      발생했는지(4a도 알람이 이미 있으니 텔레그램 히스토리로 확인 가능)부터 보고, 3)번(429
      알람)을 먼저 붙인 뒤 그 결과를 보며 이 항목의 설계를 재판단하는 순서를 추천.
    * **[저장소 소유자 코멘트, 2026-07-29]** 다행히 아직까지 503, 429 모두 발동한적 없어.
      그렇지만 우선순위는 우리 큐 수준에서 순차처리로 제어하고, 그렇게 했음에도 주간리밋
      등을 초과하게 되면 429를 대응하는게 맞다고 봐. 물론 groq는 주간 리밋은 없는거 같지만,
      만약 다른 llm 어댑터를 쓸 경우 존재할 수 있거든. 현재로썬 over-engineering이지만
      예외처리를 단단하게 구현해둬도 나쁠건 없는거 같아.
    * **[Claude 후속 코멘트, 2026-07-29]** 우선순위를 큐(순차처리 정정)를 먼저, 429 방어를
      나중으로 재조정하는 것에 동의. 이건 "REQUEST_QUEUE_MAX/큐"라는 이름과 실제 즉시거절
      동작이 어긋나 있던 부분(CLAUDE.md의 "request queuing is still TBD" 오픈퀘스천)을 바로
      고치는 것이기도 해서, 알람 추가보다 오히려 더 근본적인 정정으로 볼 수 있음. 다른 LLM
      벤더로 교체될 가능성(PRD §8 "벤더 교체 = 어댑터 1지점 교체")을 감안하면 429 예외처리를
      벤더 종류에 무관하게 단단히 짜두는 것도 합리적 — 동의.

3) 4b 항목
    * 429, 422, 409에 대해 폴백처리가 전무함.
    * 4XX 응답상태코드가 발생하면 알람을 보낼 것. (그럴 일은 없겠지만, 악의적 공격에 대해서 과도한 알람을 방지하기 위해 동일 알람 발생 시 5분마다 알람보낼 것.)
    * **[Claude 코멘트, 2026-07-29]** "폴백처리가 전무함"은 429/422/409만의 특징이 아니라
      500/502를 포함한 전체 에러 경로의 공통 특성(이 앱엔 애초에 "실패 시 대체 로직으로
      넘어가는" 폴백 개념 자체가 없고, 재시도 소진 후엔 항상 에러 반환뿐)이라 "폴백 추가"보다
      "알람 대상 확대"로 스코프를 좁히는 게 정확함. 429·422를 알람 대상에 넣는 것에는 강하게
      동의 — 429는 이미 503(Inflight)에 있는 "용량 부족 시 알림" 선례와 일관성을 맞추는
      것뿐임. 다만 **409는 다르게 봄**: 429/422는 "서비스가 못 버팀/LLM이 이상하게 응답함"(운영자
      조치 가능)인 반면, 409(NO_SETLIST)는 대부분 "밴드 필터를 너무 좁게 + 재생시간을 너무
      길게" 같은 애초에 불가능한 요청 조합이라 운영자가 즉시 조치할 수 있는 상황이 아님 —
      실시간 알람보다 로그로 빈도만 누적 관찰(자주 발생하면 프론트 사전 안내 강화)을 추천.
      400(형식 오류)은 이 항목에서도 우려한 대로 봇/악성 트래픽에 노출된 엔드포인트라 계속
      알람 제외를 추천 — 5분 스로틀이 있어도 봇이 계속 두드리면 하루 최대 288번(5분마다)씩
      무한정 울릴 수 있음. **정리: 429·422는 알람 O, 409는 알람 대신 로그 집계, 400은 계속
      알람 제외.**
    * **[저장소 소유자 코멘트, 2026-07-29]** 409는 사용자에게 다른 조건으로 이용해달라고
      안내해주면 되는 문제야. 이건 현재도 이에 대한 대응 안내가 존재하지? 없으면 사용자로
      하여금 적절히 이용할 수 있도록 안내하게 해. 이건 나한테 알람을 보낼 필요는 없을거 같아.
      400은 저런 상황이 발생하면 일단 내가 모니터링을 해야하거든. 누가 실수한건지, 아니면
      악의적으로 시도한건지 말야. 어찌됐든 400이 일정 한도 이상으로 발생하면 긴급셧다운을
      할 계획이야. 이에 대해 대응책도 세워야겠지만, 그건 정형화된 방법이 없다면 그때 상황봐서
      세워야 될 문제 같아.
    * **[Claude 후속 확인, 2026-07-29]** 409 안내 존재 여부를 `src/frontend/app.js`에서 직접
      확인함 — 프론트는 에러코드별 분기 없이 `data.error.message`를 공통 에러 배너에 그대로
      표시하는 구조뿐(`app.js:112-115`, 제출 핸들러의 `if (!res.ok) { ... throw new Error(msg) }`).
      409의 백엔드 메시지는 "조건에 맞는 세트리스트를 만들
      수 없습니다."(`main.py:372`)로, **에러가 떴다는 사실은 안내되지만 "선택한 밴드를 더
      추가해 보세요", "재생 시간을 줄여 보세요"처럼 사용자가 바로 따라 할 수 있는 구체적
      행동 가이드는 없음** — 요청대로 추가가 필요한 상태. (※ 최초 초안이었던 "밴드 필터를
      줄이세요"는 "줄인다"가 밴드 수를 늘리라는 건지 조건을 완화하라는 건지 모호해서, 사용자
      관점에서 바로 이해되는 문구로 수정함.)
      400 모니터링 건은 이전 코멘트에서 "노이즈 우려로 알람 제외"를 추천했는데, 목적이
      보안 모니터링(실수/악의 구분, 긴급 셧다운 판단 근거)이라면 노이즈보다 가시성이 우선이라는
      점에 동의 — 이미 있는 5분 동일-title 스로틀이 노이즈는 어느 정도 흡수하므로 이 목적에는
      알람 포함이 맞다고 의견 정정. 자동 셧다운 임계치·정책은 지금 정형화하지 않고 필요 시점에
      정하는 것에도 동의(섣부른 자동화가 더 위험할 수 있음).

4) main.py
    * research 브랜치에서 진행한 연구 llm_param_control_separate에서 적용하기로 한 GROQ_MULTISTAGE가 구현만 되어 있고 실적용은 안되어있음.
    * 추후 현재 main을 기준으로 재검증 후 현재 버전보다 개선된 사용 및 청취감이 있는 경우 이를 적용.
    * **[Claude 코멘트, 2026-07-29]** 기존에 이미 결정된 사안과 일치함(메모리
      `decision-enable-groq-multistage-pending-review` — main엔 병합됐지만 Render엔
      `MOOD_INTERPRETER` 미설정이라 단일호출로 서빙 중, main.py 코드 리뷰 후 전환 예정). 다른
      의견은 없으나, "재검증 후 개선되면 적용"이라는 조건에 **구체적인 재검증 시점**을 하나
      정해두는 걸 추천 — 지금 문구만으로는 무기한 보류로 남을 위험이 있음.
    * **[저장소 소유자 코멘트, 2026-07-29]** 이건 해야지. 작업 우선순위는 작업 시작 전에
      논의하자고.
